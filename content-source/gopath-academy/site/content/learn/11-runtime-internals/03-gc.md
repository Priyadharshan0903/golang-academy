## How the collector works

Go's garbage collector is a **concurrent, tri-color, mark-and-sweep** collector. In plain words:

1. **Mark.** Starting from the **roots** (global variables and every goroutine's stack), the GC follows pointers and marks every object it can reach. This runs **concurrently** with your program, on about 25% of the CPU, plus "assists": goroutines that allocate quickly during marking are asked to help, so allocation cannot outrun the collector.
2. **Sweep.** Memory of unmarked objects is reclaimed, lazily, as new allocations need space.

While marking runs, a **write barrier** (a little extra work on pointer writes) tells the GC about pointers your program moves around, so nothing reachable is missed. There are two short **stop-the-world** pauses per cycle, typically well under a millisecond.

Two design choices to know:

- **Non-generational.** Every cycle marks the whole live heap. The cost of a cycle is proportional to the **live** heap (and the number of pointers in it), not to the garbage.
- **Non-moving.** Heap objects never move. (Stacks do, lesson 11.2.)

So the GC's total cost is roughly: **(cost per cycle, driven by live heap) × (number of cycles, driven by allocation rate and GOGC)**. You reduce it by allocating less (lesson 10.4), by keeping fewer pointers in the live heap, or by running fewer cycles.

## GOGC: trading memory for CPU

`GOGC` sets how much the heap may grow before the next cycle. With the default `GOGC=100`, the next cycle starts when the heap has grown by 100% of the live heap (plus GC roots such as stacks and globals):

```text
heap goal = live heap + (live heap + GC roots) × GOGC / 100
```

Results on the 2-core test VM with Go 1.27:

```text
GOGC=50   cycles=58  heap goal about  26 MiB
GOGC=100  cycles=31  heap goal about  35 MiB
GOGC=200  cycles=15  heap goal about  52 MiB
GOGC=400  cycles=7   heap goal about  93 MiB
GOGC=off GOMEMLIMIT=64MiB: cycles=13  heap goal about  55 MiB
```

Each doubling of `GOGC` roughly halves the number of GC cycles and roughly doubles the extra memory above the live heap. Numbers vary between runs, and a lot on a busy machine, so the test only asserts the broad trend. There is no free lunch, only a dial: memory or CPU.

You can also set it in code with `debug.SetGCPercent`, and `GOGC=off` disables the collector entirely (dangerous on its own: memory grows without bound).

## GOMEMLIMIT: a ceiling

`GOMEMLIMIT` (Go 1.19) sets a **soft limit** on the total memory the Go runtime uses: heap, stacks and runtime structures. Values look like `GOMEMLIMIT=512MiB`, or plain bytes. As memory approaches the limit, the GC runs more often, whatever `GOGC` says.

The last line of the experiment combines `GOGC=off` with a 64 MiB limit: no cycles until the heap approaches the limit, then just enough to stay under it. That configuration makes the GC run as rarely as possible within a known memory budget, ideal for batch jobs with a fixed amount of memory.

For services in **containers**, the most useful setting is a limit a little **below the container's memory limit**, leaving 5 to 10% of headroom for memory the runtime does not control (cgo, the binary itself). With a pod memory limit of 1 GiB, `GOMEMLIMIT=900MiB` lets the GC work harder as memory gets tight, instead of the kernel killing the pod with OOMKilled. Keep `GOGC` at its default alongside it. Module 15 sets this in a Kubernetes manifest.

The limit is soft for a reason: if the live heap itself exceeds the limit, collecting constantly would freeze the program (a "death spiral"). The runtime caps GC CPU use at about 50% in that situation, so the program stays responsive and may go over the limit. A real leak still needs fixing.

## Reading gctrace

`GODEBUG=gctrace=1` prints one line per cycle to standard error:

```bash
GODEBUG=gctrace=1 go run ./examples/m11/gc/gcdemo
```

```text
gc 6 @0.015s 5%: 0.031+0.53+0.003 ms clock, 0.063+0.33/0.019/0+0.006 ms cpu, 28->31->18 MB, 33 MB goal, 0 MB stacks, 0 MB globals, 2 P
```

| Part | Meaning |
|---|---|
| `gc 6 @0.015s` | the 6th cycle, 15 ms after start |
| `5%` | share of CPU used by the GC since the program started |
| `0.031+0.53+0.003 ms clock` | first stop-the-world pause + concurrent mark + second pause. The pauses are microseconds. |
| `28->31->18 MB` | heap at cycle start → heap at mark end → **live heap** after marking |
| `33 MB goal` | the heap goal for this cycle |
| `2 P` | GOMAXPROCS |

If you see cycles many times per second with a small live heap, the program is allocating heavily: reduce allocations, or raise `GOGC`. If the live heap keeps growing, look for a leak with a heap profile (`inuse_space`, lesson 10.2).

## Green Tea (Go 1.26)

Go 1.25 shipped a new marking algorithm, **Green Tea**, as an experiment, and Go 1.26 made it the default. Instead of following pointers object by object around the heap, it scans memory **page by page**, batching the small objects that live together, which gives much better CPU cache locality and scales better to many cores. The Go team expects **10 to 40% less GC overhead** for programs that use the GC heavily, and about 10% more on recent amd64 CPUs that can use vector instructions for scanning.

Nothing changes in your code; you get it by upgrading. For now an opt-out exists, `GOEXPERIMENT=nogreenteagc` at build time, but it is planned for removal, so if you need it, report why.

## Weak pointers and cleanups (Go 1.24)

Sometimes you want to refer to an object **without** keeping it alive, for example in a cache keyed by large values. The `weak` package provides **weak pointers**:

{{< example file="examples/m11/gc/gc.go" region="weak" run="go test -v -run TestWeak ./examples/m11/gc" >}}

`w.Value()` returns the object while something else keeps it alive, and `nil` once it has been collected. Note the `alive` helper: `Value` returns an ordinary pointer, and while that pointer is in use, the object stays alive. This is easy to get wrong: an earlier version of this example checked `w.Value() != nil` directly inside `WeakDemo`, and in the test the Blob survived the `runtime.GC()` call: the temporary pointer from `Value` was most likely still considered live. Moving the check into its own small function fixed it.

`runtime.AddCleanup` runs a function after an object becomes unreachable, for example to release a non-memory resource it wraps:

Cleanups replace the older `runtime.SetFinalizer`, which had sharp edges (finalizers could resurrect objects and prevented collecting cycles). Two rules: the cleanup function must not refer to the object itself (pass what it needs as the argument), and cleanups may run late or not at all before the program exits. Close files and connections explicitly with `defer`; use cleanups only as a safety net.

## Common mistakes

### Tuning GOGC before reducing allocations

Allocation reduction lowers both CPU and memory. GOGC only moves cost from one to the other.

### No GOMEMLIMIT in a memory-limited container

Without it, the GC does not know about the container limit. Heap growth between cycles can push the process over the limit, and the kernel kills it.

### Setting GOMEMLIMIT equal to the container limit

Leave headroom for non-heap memory, or the kernel may still kill the process first.

### Relying on cleanups or finalizers for correctness

They are not guaranteed to run promptly or at all. Release resources explicitly.

## Key takeaways

- Go's GC is concurrent mark-and-sweep, non-generational and non-moving; pauses are short, cost scales with the live heap and the number of cycles.
- `GOGC` trades memory for CPU: doubling it roughly halves cycles and doubles heap overhead.
- `GOMEMLIMIT` is a soft memory ceiling; in containers, set it 5 to 10% below the memory limit.
- `GODEBUG=gctrace=1` shows every cycle: pauses, heap sizes and goal.
- Green Tea is the default collector since Go 1.26.
- `weak.Pointer` refers to objects without keeping them alive; `runtime.AddCleanup` replaces `SetFinalizer`.
