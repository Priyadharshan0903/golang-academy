## What you will learn

- The kinds of test doubles: stubs, fakes, spies and mocks
- Why Go code usually needs no mocking framework
- How to design code so dependencies are easy to replace
- When to test against the real thing instead

## The idea

Code that sends email, charges cards, reads the clock or calls other services is hard to test directly: the dependencies are slow, cost money, have side effects or change over time. The fix is to make the dependency an **interface** the code accepts (lesson 4.8), and give it a **test double** in tests.

Go's implicit interfaces make this cheap: a test double is just a small struct with the right methods, written in a few lines.

## Kinds of test doubles

| Kind | What it does | Example above |
|---|---|---|
| **Stub** | Returns canned answers | `fixedClock` |
| **Fake** | A working but simplified implementation | an in-memory store instead of Postgres |
| **Spy** | Records how it was called, for the test to inspect | `fakeMailer.sent` |
| **Mock** | Pre-programmed with expectations, fails if calls differ | (generated by a library) |

In Go, **hand-written fakes and spies** are the norm. They are explicit, need no reflection, and survive refactoring better than mocks that assert the exact sequence of calls.

## Design for replaceability

- **Accept small interfaces** defined by the consumer (lesson 4.2). A two-method `Mailer` is trivial to fake; a 30-method `CloudClient` is not.
- **Inject dependencies** through struct fields or constructor parameters, not package-level globals.
- **Make time, randomness and IDs dependencies** too: a `Clock` interface or a `now func() time.Time` field (the shortener and rate limiter projects do this).
- **Keep fakes close to the interface**, so several test packages can share them. A common place is a `xxxtest` package, like the standard library's `httptest` and `fstest`.

## When to use a mocking library

Generators like `go.uber.org/mock` (`mockgen`) or `github.com/vektra/mockery` create mocks from interfaces. They help when an interface is large, when you need to check call order or counts precisely, or when many tests need the same doubles. Use them sparingly; tests full of `EXPECT()` calls tend to test the implementation rather than the behavior.

## When to use the real thing

Test doubles prove your code works **with your assumption** about the dependency. They cannot prove the assumption is right. So also test against real implementations where it is affordable:

- **Databases**: run tests against a real PostgreSQL in a container (lesson 13.x) for the storage layer.
- **HTTP APIs**: test your client against `httptest.Server` with realistic responses, and run a few tests against the real API in a separate, opt-in suite (lesson 9.8).
- **Filesystem**: `t.TempDir()` is fast and real; there is rarely a reason to fake `os`.

A healthy suite has many fast unit tests with fakes and fewer, slower integration tests with real dependencies.

## Common mistakes

### Interfaces that exist only for mocking

Do not add an interface to every type "so it can be mocked". Add it where a consumer needs a replaceable dependency.

### Mocks that mirror the implementation

A test that asserts "calls `Get`, then `Set`, then `Get`" breaks when the code is refactored, even though behavior is unchanged. Assert outcomes.

### Fakes that diverge from reality

A fake store that never returns errors hides your error handling paths from tests. Give fakes a way to fail.

## Key takeaways

- Replace slow or side-effecting dependencies with test doubles behind small interfaces.
- In Go, hand-written stubs, fakes and spies are usually enough.
- Inject dependencies, including time and randomness.
- Use mocking libraries sparingly; assert behavior, not call sequences.
- Complement fakes with integration tests against real dependencies.
